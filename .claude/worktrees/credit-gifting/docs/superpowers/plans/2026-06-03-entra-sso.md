# Enterprise Entra SSO (per-org OIDC + SAML) — Implementation Plan (Spec 3a)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`).

**Goal:** Per-org enterprise SSO against Microsoft Entra ID via OIDC (Assent) and SAML (real, `esaml`), with email-domain login routing and JIT provisioning into the org — reusing the existing `user_identities` + verified-email account-link guard. SCIM is Spec 3b.

**Architecture:** A new `PerfectPaper.SSO` context owns `org_sso_configs` + the flow. `SSO.Provider` behaviour (per-org, multi-protocol) returns the normalized `identity` map the OAuth seam already uses; adapters `SSO.OIDC` (Assent, tenant-scoped Entra), `SSO.SAML` (esaml, per-org dynamic, full signature validation), `SSO.Stub` (tests). Login routes by verified email domain; callback resolves identity (reusing `Accounts` JIT guards) + ensures org membership. Security: domain verification gates routing+JIT; SAML signature validation mandatory; secrets hidden.

**Tech Stack:** Elixir/Phoenix 1.8, Assent (present), **esaml** (new) + xmerl/`:public_key` for SAML, Ecto/Postgres. Spec: `docs/superpowers/specs/2026-06-03-entra-sso-design.md`.

## Conventions
Architecture laws; `@spec`/`@doc`/`@type`; adapter pattern (no IdP/lib specifics past the adapter; adapters return the atom-keyed `identity` map); org-admin gating via `Organizations.admin?`; `TODO(sso)` for deferred items (credential encryption-at-rest, DNS-TXT automation). NO real Entra/IdP calls in tests — use `SSO.Stub` + signed-fixture assertions for SAML.

## Security hardening (from review — MANDATORY; applies to Tasks 4, 6, 7)
Runtime is **Erlang/OTP 29** (xmerl disables entity expansion by default — so the default-on XXE exposure is not active here), but these are required regardless (defense-in-depth):
- **SAML XXE (Task 7):** parse attacker-controlled SAML with **external-entity loading DISABLED** — pass xmerl options that forbid external entities / supply a no-op entity resolver (do NOT rely on the OTP-29 default). Enforce a **max payload size + base64/XML shape guard BEFORE parsing**. Pin the esaml version and confirm it carries the CVE-2026-28809 (pre-signature XXE) fix; if the upstream is unpatched, use a patched fork or wrap the parse. Parsing happens before signature checks, so XXE-safety must not depend on signature validity.
- **SAML XSW — XML Signature Wrapping (Task 7):** populate the `identity` **ONLY** from esaml's cryptographically-validated assertion struct. **NEVER** run `xmerl_xpath`/manual XPath on the raw document to pull email/uid/name — that's the classic wrapping-attack hijack. A test must cover a wrapped/dual-assertion payload → rejected or only-the-signed-block used.
- **SAML replay / InResponseTo (Tasks 6 + 7):** persist the generated AuthnRequest ID in the **encrypted Phoenix session cookie** (`put_session`) at redirect — node-agnostic, so a clustered callback on a different node still validates. On callback, assert the response's `InResponseTo` matches the stored ID, then **delete it (one-time consume)** → replay-proof. Reject if missing/mismatched. (Same for OIDC `state`/nonce via Assent session_params, already cookie-backed.)
- **Domain routing (Tasks 1/4):** **exact-match only** (already implemented — `Repo.get_by(email_domain:)`, no subdomain hierarchy crawl). `sub.company.com` does NOT inherit `company.com`'s SSO → falls back to normal login (secure default). Widen the public-domain blocklist substantially and add `TODO(sso): source the freemail blocklist from a maintained dataset/lib` (the hardcoded list is a stopgap, prone to omission).

## Security hardening — ROUND 2 (from review; MANDATORY)
- **(1) esaml XXE bypass (Task 7):** do NOT call `esaml_binding:decode_response/2` (it runs `xmerl_scan` with no safe options internally). Instead, in the adapter: base64-decode (and inflate for the redirect binding) the raw SAMLResponse yourself, enforce a max-size/shape guard, then parse with the CONFIRMED XXE-safe wrapper and hand the **pre-parsed** doc to `esaml_sp:validate_assertion/3` (esaml accepts pre-parsed XML):
  ```elixir
  xml_charlist = String.to_charlist(raw_xml_string)
  try do
    {xml_doc, _rest} = :xmerl_scan.string(xml_charlist, [{:allow_entities, false}, {:quiet, true}])
    {:ok, xml_doc}
  catch
    _exit, error -> {:error, {:xml_parse_failed, error}}
  end
  ```
  `{:allow_entities, false}` blocks entity expansion explicitly (defense-in-depth independent of the OTP-29 default); `{:quiet, true}` suppresses stdout on malformed XML. Test: an XXE-payload assertion neither fetches nor expands the external entity (and is rejected).
- **(2) Admin domain-change hijack (Task 4 — FIX committed code):** in `configure_sso`, if the update changes `email_domain` OR any IdP metadata/credential field, **force-reset `domain_verified=false` and `enabled=false`** in the same change (admin must re-verify + re-enable). Prevents a compromised/abusing admin from repointing a verified+enabled config at a new domain to hijack its logins. Test: changing the domain of a verified+enabled config resets both flags.
- **(3) Unified guest promotion (Task 7.5):** a SINGLE `Accounts.promote_guest(user, attrs)` transaction is the ONLY promotion path — BOTH `register_user` (on an existing guest email) AND the SSO JIT resolution (`resolve_sso_identity` matching an existing guest) route through it, so role transition + audit + the one-time `:signup` credit happen identically (no drift).
- **(4) Domain sanitization (Task 1 — FIX committed code):** `SsoConfig.changeset` must sanitize `email_domain` BEFORE validation/unique: `String.trim |> String.downcase |> String.replace_leading("@","") |> strip trailing "/"/whitespace`. Apply the SAME normalization to the domain extracted in `SSO.config_for_email/1` so stored + lookup values match. Test: `"@Company.com "` stored as `"company.com"`; a login email in that domain routes.
- **(5) Concurrent-tab request IDs (Tasks 6/7):** store pending SSO request IDs as a session MAP keyed by org — `put_session(conn, :sso_requests, Map.put(existing, org_id, request_id))`. On `/sso/:org_id/callback`, read `sso_requests[org_id]`, validate `InResponseTo`/state, then delete JUST that key. Prevents a second concurrent login tab (different org) from clobbering the first's request ID.

## Security hardening — ROUND 3 (JIT identity resolution; MANDATORY for Tasks 5, 6, 7.5)
The SSO resolver runs only AFTER the Task 5 domain-match guard (asserted email is IdP-verified AND inside the org's Task-4 **verified, proven-owned** domain). Given that, handle an EXISTING local user with an UNVERIFIED email by its CREDENTIAL STATE — never the old blanket `:email_taken` (a DoS lockout) and never a naive auto-link (the nOAuth backdoor):
- **Rule 1 — invited guest (NO password hash):** safe → route through `Accounts.promote_guest/2`: link the SSO identity, mark email verified, transition role to member, fire the one-time `:signup` credit. (No password ⇒ no backdoor.)
- **Rule 2 — self-registered-but-unverified WITH a password hash (potential email-squatter):** **neutralize, then link** — (a) nullify/disable `hashed_password` (or a `password_login_disabled` flag), (b) **revoke ALL active sessions** for that `user_id` (delete their `user_tokens`), THEN (c) link the SSO identity + mark email verified. This simultaneously fixes the **DoS** (the legit exec now logs in via SSO) and kills the **backdoor** (the squatter's password + sessions are obliterated). Safe ONLY because of the verified-domain proof.
- Verified-email existing account → link as today.
- **Scope distinction (do NOT weaken social login):** Rule 2's neutralize-and-link is justified ONLY by the verified-domain proof, so it applies to the **enterprise-SSO** resolver path. The existing generic OAuth (`Accounts.sso_sign_in` for google/github — no domain ownership proof) KEEPS its `:email_taken` guard for a squatted password. Rule 1 (guest, no password) is safe for both. So the SSO resolver needs a "trusted/verified-domain" signal; the OAuth path stays unchanged. Keep existing OAuth tests green.
- **Mixed-case domain (Task 5):** sanitize the asserted identity's email domain via `SsoConfig.sanitize_domain/1` BEFORE the domain-match comparison — Entra returns mixed-case (`Alice@Acme.COM`); both sides must be normalized or logins fail spuriously.
- **Session cleanup (Task 6):** delete the `org_id` key from the `:sso_requests` session map on BOTH successful login AND terminal failure/rejection (no stale request IDs / cookie bloat).

### Credential-flexibility rule for promote_guest (from review)
`promote_guest` is the unified boundary for TWO credential states — design it so the SSO path never trips password validation:
- **Password mode** (standard registration UI): cast + validate + hash the password.
- **SSO mode** (Task 5 JIT): NO password — must NOT require/validate a password; leave `hashed_password` nil/untouched.
Implement via distinct entry points / two specialized changesets under ONE atomic transaction — e.g. `promote_guest(user, :sso, attrs)` (no password) vs `promote_guest(user, :password, attrs)` (password), or `sso_promotion_changeset/1` + `password_promotion_changeset/2`. Both do confirm + idempotent `:signup` credit + role/`promoted_at` transition.
**Form-field compatibility (from review):** `password_promotion_changeset/2` MUST run the SAME password validation rules and return a changeset structurally identical to the standard registration changeset — same field names (`password`/`password_confirmation`) and error keys — so the registration LiveView binds inline errors for a guest-promotion signup with ZERO template changes (and never crashes on `{:error, changeset}`). Reuse the existing registration password changeset directly. **Test a FAILING password-promotion** (too-short/invalid password) → `{:error, changeset}` with `errors_on` showing the same `:password` key a fresh signup produces. **The returned changeset MUST have `changeset.action` set** (`:update`/`:insert`) — Ecto stamps it on a `Repo` op, but a pre-Repo validation short-circuit leaves it `nil`, which makes Phoenix SILENTLY HIDE all inline form errors. The failing-validation test must assert `changeset.action != nil`.

## SAML/esaml interop traps — ROUND 4 (MANDATORY for Task 7)
esaml is pure Erlang; these cause runtime crashes / signature failures / bypasses if missed:
- **(1) Charlist → binary:** esaml returns **charlists** in `#esaml_assertion{}`/`#esaml_subject{}` (NameID, issuer, attribute keys/values). Convert ALL extracted strings to binaries via `List.to_string/1` (and map attributes: `Map.new(attrs, fn {k,v} -> {List.to_string(k), Enum.map(v, &List.to_string/1)} end)`) BEFORE building the `identity` map — else `sanitize_domain`/case-ops crash and Ecto corrupts the column.
- **(2) POST base64 only — NO inflate:** the inbound callback `SAMLResponse` (HTTP-POST binding) is base64-encoded but **NOT deflated**. Base64-decode only; do NOT inflate/decompress (that's the redirect *request* binding) — inflating the POST response crashes zlib (`:data_error`).
- **(3) PEM → DER for the IdP cert:** `saml_idp_cert` is stored as PEM text; esaml/`:public_key` need the **DER** binary. Decode before building the SP: `case :public_key.pem_decode(pem) do [{:Certificate, der, _}|_] -> {:ok, der}; _ -> {:error, :invalid_pem_certificate} end`. Passing raw PEM → `:badmatch` deep in `:public_key.verify`.
- **(4) Signature location (envelope vs assertion):** esaml defaults `require_signed_assertions: true`; some Entra/ADFS tenants sign only the **response envelope**. Set a strict baseline (`require_signed_assertions: true`) and **TEST BOTH** fixtures (assertion-signed AND envelope-signed); document how an envelope-signing client is supported (`require_signed_envelopes`). Never disable signature checking to "make it work".
- **(5) Namespace prefixes:** IdPs vary (`saml2:`/`samlp:`/`saml2p:`/default ns). Test fixtures must use Microsoft Entra's typical `saml2:`/`saml2p:` prefixes to prove the XXE-safe parse wrapper handles them without exits.

## Task 7.5 (NEW, from review): Guest-to-member promotion
**Files:** `lib/perfect_paper/accounts.ex`; tests. **The gap:** `find_or_create_guest` creates a real `users` row by email (no signup credit). Today a guest is still usable (magic-link; SSO `link_or_create` links to the existing record), BUT the self-service **register** path (`register_user` on an existing email) errors `:email_taken`, and a self-promoting guest never receives the deferred `:signup` credit.
- Add `Accounts.promote_guest(user)` (or handle in `register_user`): when a self-initiated signup/SSO targets an existing **guest** record (a user with no prior self-signup), treat it as a **promotion** — keep the record (don't error), and fire the `:signup` credit campaign **once** at promotion (guard against double-granting if already promoted/credited). Define "guest" (e.g. created via invite, never self-completed signup — a `promoted_at`/flag, or derive from "has only resource_grants + no password and no prior signup credit").
- `register_user`/the registration flow: on an existing guest email, promote + log in rather than `:email_taken`; on an existing **full member**, keep the existing "already registered, just log in" behavior.
- Tests: invite a guest (no credit) → guest self-registers/SSO-signs-in → promoted, `:signup` credit granted exactly once; a full member re-registering is unaffected; double-promotion doesn't double-credit.
- Sequence this AFTER Task 5 (SSO sign_in) and before Task 9. (It's an Accounts concern that the SSO JIT flow also exercises.)
